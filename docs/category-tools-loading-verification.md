# 방송 목록 검색·썸네일·스크롤 개선 검증

## 원인 확인 — 2026-09-12 KST

대상은 Chrome의 `https://chzzk.naver.com/lives`와 현재 branch `1.3.6`의 작업 파일이다. HEAD는 `a2d83eb`이고 manifest/package 버전은 `1.3.5`로 유지했다.

- 실제 `talk` 검색에서 확장이 추가한 카드 114개 모두 썸네일 `src`가 없고 `naturalWidth`가 0이었다. 기존 이미지 URL 검사가 `pstatic.net`과 치지직 도메인만 허용하여 API가 반환한 `livecloud-thumb.akamaized.net` 이미지를 제거했다.
- 실제 목록 API의 `liveImageUrl` 및 네이티브 카드가 이 호스트를 사용하는 것을 확인했다. 측정한 `/chzzk/livecloud/KR/stream/26428721/live/21061396/record/58999967/thumbnail/image_720.jpg`는 HTTP 200, `image/jpeg`로 응답했다.
- 검색 시 집계용으로 미리 받은 메타데이터까지 한꺼번에 카드로 생성했다. 같은 150개 fixture에서는 기존 코드가 추가 카드 148개를 첫 적용에서 만들었다.
- 필터가 없어도 진행 시간 배지가 켜져 있으면 스크롤에서 전체 `applyTools()`를 예약했다. 200ms 안에 끝나는 마지막 스크롤 이벤트도 별도 후속 확인 없이 버렸다.
- 추가 카드의 프로필은 화면에서 작게 표시하면서 3,000~3,840픽셀 원본을 디코딩했다. 네이티브 프로필의 `type=f160_160_na` 형식을 확인했고, 동일한 3,840픽셀 원본 URL에 이 형식을 사용한 응답은 HTTP 200, 160×160이었다.

## 변경 사항

- `livecloud-thumb.akamaized.net` 정확한 호스트만 이미지에 허용했다. 다른 Akamai 호스트·접미사 위장·하위 호스트는 거부하고 미디어 실행/스트림 허용 범위는 늘리지 않았다.
- 추가 카드 이미지에는 `loading="lazy"`, `decoding="async"`를 적용했다. 원본 크기로 제공된 `nng-phinf.pstatic.net` 프로필에는 네이티브의 160픽셀 형식을 사용한다.
- 추가 카드 생성은 24개 단위로 진행하고, 아래로 이동하면 캐시의 결과부터 이어서 표시한다. 검색·필터를 바꾸면 이전 조건의 확장 소유 카드를 제거한다. 네이티브 카드를 제거하거나 재부모화하지 않는다.
- 일반 검색은 팔로워 배지를 기다리지 않고 표시하며 화면 근처의 결과만 보충 조회한다. 팔로워 필터는 다른 조건을 통과한 후보를 별도로 조회하므로 아직 DOM 카드가 없는 후보도 계속 확인한다.
- 팔로워 조회는 실측한 `/service/v1/channels/{channelId}/followers/count`를 사용하며 기존 캐시·동시성·묶음·간격 설정을 유지한다. 진행 중·빈 결과·팔로워 조회 실패를 구분한다.
- 일반 스크롤은 기억한 카드 행의 배지만 보충한다. 마지막 스크롤 확인은 한 번만 예약하고, 페이지 이동·옵션 비활성화 시 취소한다. 메뉴 위치는 열린 경우에만 프레임 단위로 갱신한다.
- 동일한 메타데이터 탐색 요청은 진행 중인 탐색을 다시 시작하지 않는다. 현재 페이지에서 관측한 시청자순·시청자역순·최신순·추천순 레이블을 인식하여 다른 정렬에 인기순 API 결과를 섞지 않는다.

## 자동 검증

- 변경 전 실패를 확인한 회귀 범위: 실제 썸네일 호스트, 팔로워 응답과 검색 표시 분리, 스크롤의 전체 적용 제거, 추가 카드 생성량 제한.
- 150개 fixture에서 첫 추가 카드 148개 → 24개를 확인했다. 이후 스크롤마다 최대 24개씩 추가하여 전체 150개를 중복 없이 표시했고, 이미 받은 페이지는 재요청하지 않았다.
- 아직 카드가 없는 팔로워 후보 처리, 실패와 빈 결과 구분, 동일 요청 공유, 마지막 스크롤 예약·취소, 현재 정렬 레이블, 악성 이미지 URL 거부를 확인했다.
- 기존 DOM 재사용·재마운트·옵션 해제·SPA 취소 및 늦은 응답 보호 검사를 유지했다. 이전 조건의 주입 카드를 숨겨서 남기던 검사는 해당 노드가 DOM에서 제거되는지 확인하도록 변경했다.
- 최종 `npm.cmd run test:all`: 605개 통과, 실패 0개.
- `npm.cmd run lint`, `npm.cmd run format:check`, `git diff --check` 통과.

## 실제 Chrome 검증

- 브라우저 도구가 확장 관리 페이지 접근을 차단했다. 우회하지 않고 사용자가 Better Chzzk를 직접 새로고침한 뒤 대상 치지직 탭을 브라우저 도구로 새로고침했다.
- 새 검색 UI와 DOM 마커, 추가 카드 수 제한, 썸네일 URL·`loading`·`decoding` 속성으로 변경 코드의 동작을 확인했다.
- `talk` 검색 첫 추가 카드 24개에서 누락된 썸네일 `src`는 0개였다. 화면 안의 추가 카드 이미지에 실제 픽셀 크기가 잡히고 화면에도 표시되는 것을 확인했다.
- 추가 결과의 링크에 키보드 초점을 두고 아래로 이동하여 24개 → 48개, 표시 결과 41개 → 65개로 이어지는 것을 확인했다. 목록 메타데이터는 650개로 유지됐다. 방송 목록 자체는 실시간으로 변하므로 이전 재현과 전체 개수가 다를 수 있다.
- 마지막 스크롤 예약과 프로필 크기 보완 후 사용자가 확장을 다시 새로고침했고, 치지직 페이지도 새로고침했다. 최종 추가 카드 24개에서 썸네일 주소 누락은 0개였으며, 확인한 프로필 3개 모두 `type=f160_160_na`, 실제 너비 160픽셀이었다.
- 라이트 모드에서 채널명 검색과 팔로워 최소 1명 필터가 결과 1개를 표시했고, 해당 썸네일과 160픽셀 프로필이 실제로 로딩됐다. 필터 초기화와 검색 지우기 후 주입 카드 0개, 숨겨진 카드 0개로 원래 목록이 복원됐다.
- 네이티브 카테고리 링크로 `/category/ETC/talk/lives`에 SPA 이동한 뒤 툴바 1개, 추가 카드 0개, 빈 검색어 상태를 확인하고 전체 방송으로 복귀했다. 검증 후 원래 다크 모드로 복원했다.
- 최종 코드로 복귀 후 다시 스크롤한 화면에서는 표시 중인 추가 카드 썸네일 20개 모두 로딩됐고, 확인한 프로필 3개 모두 160픽셀이었다. 마지막으로 검색 조건을 지워 원래 전체 방송 목록 상태로 돌려놓았다.
- 확장 옵션 켜기·끄기 및 늦은 응답의 정리는 자동 테스트로 확인했다. 확장 관리/옵션 페이지의 실제 브라우저 조작은 도구 접근 제한으로 수행하지 않았다.
- 프레임 시간/FPS의 정량 비교, 확장 실행 컨텍스트와 전체 콘솔 로그 수집은 수행하지 않았다. 카드 생성량과 반복 작업 감소를 실제 FPS 수치로 환산하지 않는다.

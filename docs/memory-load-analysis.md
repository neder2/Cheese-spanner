# 메모리·부하 분석 — 2026-09-09

대상은 `codex/1.3.4-refactor`의 현재 작업 트리(HEAD `a935248`, 미커밋 리팩터링 포함)다. 런타임 코드를 수정하지 않고 실제 브라우저 표본, 별도 데이터 벤치마크, 소스의 보유 상한을 함께 분석했다.

## 해석 범위

**아래 브라우저 수치는 확장 단독 사용량이 아니다.** 브라우저 도구에는 힙 스냅샷/CPU 프로파일러가 없으며, OS에서는 `chrome` 대신 `whale` 프로세스가 실행 중인 것을 확인했다. 따라서 Windows의 Whale 전체 CPU와 private working set을 측정했다. 다른 열린 탭과 다른 확장도 포함되고, GPU 전용 메모리는 별도 측정하지 않았다.

Chrome 문서도 OS 메모리와 JavaScript 힙을 구분한다. 확장 ON/OFF의 동일 조건 비교 및 힙 스냅샷 없이 이 결과를 Better Chzzk 단독 RAM/CPU로 환산할 수 없다. [Chrome 메모리 진단 문서](https://developer.chrome.com/docs/devtools/memory-problems)

## 실제 방송 수에 따른 표본

기존 탭을 건드리지 않고 진단 탭 하나에서 방송 수를 바꿨다. 측정 시점에 메인은 1920×1080, 보조 방송들은 640×360이었다. 보조 화질은 실제 플레이어가 선택한 값이며, 6개 모두 1080p인 조건은 아니다. 각 조건의 전후 재생 위치 증가와 paused=false, readyState=4를 확인했다. 드롭 프레임 API는 브라우저 도구에서 제공되지 않아 FPS/프레임 드롭은 측정하지 않았다.

| 진단 탭의 방송 수 | 실제 해상도                | Whale 전체 평균 CPU | 표본 최대 CPU | Whale 전체 private working set | 표본 시간 |
| ----------------- | -------------------------- | ------------------: | ------------: | -----------------------------: | --------: |
| 1                 | 메인 1080p                 |               5.26% |         7.87% |                      5,382 MiB |   약 12초 |
| 2                 | 메인 1080p + 보조 360p     |               5.00% |         6.22% |                      5,171 MiB |   약 12초 |
| 3                 | 메인 1080p + 보조 360p 2개 |               5.75% |         7.54% |                      5,310 MiB |   약 12초 |
| 6                 | 메인 1080p + 보조 360p 5개 |              10.80% |        14.84% |                      5,646 MiB |   약 60초 |
| 진단 탭 종료 후   | 기존 다른 탭만 유지        |              10.87% |        13.12% |                      5,301 MiB |   약 12초 |

- CPU는 2초 간격의 프로세스 누적 CPU 시간 차이를 논리 프로세서 16개와 경과 시간으로 나눈 값이다. 컴퓨터 전체 처리 용량을 100%로 본다. 프로세스별 값을 실수로 누적했다.
- RAM은 `Win32_PerfFormattedData_PerfProc_Process`의 `WorkingSetPrivate`를 Whale 프로세스 전체에 대해 더한 측정 종료 시점 값이다. 평균/최대 RAM은 아니다.
- 유효 CPU 표본의 실행 순서는 2 → 3 → 6 → 1이다. 1개 조건은 멀티뷰 종료 후 측정해서 브라우저 할당·캐시 회수의 영향을 받는다. 메모리가 단조롭게 증가하지 않는 이유를 확장 효율이나 누수로 단정하지 않는다.
- 최초 CPU 샘플러의 정수 오버로드 반올림 문제를 확인해 해당 CPU 표본은 폐기하고 실수 누적 결과만 보존했다.
- 다른 탭을 중단하지 않았고 각 조건을 여러 차례 교차 반복하지 않았다. 부하 경향을 보는 짧은 관측이며 인과관계를 증명하는 통제 실험은 아니다.
- 이번 표본에서는 6개 조건의 CPU가 1~3개보다 높았다. 현재 화면에서 보조 화질이 낮았으므로 고해상도·고프레임률의 최대 부하를 대표하지 않는다.
- **진단 탭을 닫은 뒤에도 CPU가 10.87%였으므로, 관측 차이를 멀티뷰나 확장의 추가 CPU라고 해석할 수 없다.** 다른 탭의 활동과 전경 전환에 따른 영향이 커 CPU의 기능별 순증분은 이번 측정으로 확정하지 못했다. RAM 변화도 같은 이유로 참고 표본으로만 사용한다.

원자료: [브라우저 표본](measurements/browser-profile-results.json). 진단 탭은 측정 후 닫았다.

## 데이터 구조 벤치마크

각 조건을 새 Node 프로세스에서 3회 실행했다. 같은 길이 규칙의 합성 메타데이터를 실제 repository/model에 주입하고, GC를 3회 실행한 뒤 초기 상태 대비 `heapUsed` 증가를 측정했다. 아래는 중앙값이다. 실제 네트워크, Chromium DOM, 영상 디코더, GPU, 전체 확장 초기 로드 비용은 포함하지 않는다.

| 조건                                      | GC 후 JS 힙 증가 | 캐시 명시적 정리 후 초기 대비 잔여 |
| ----------------------------------------- | ---------------: | ---------------------------------: |
| 영상 검색 1채널·600개 영상                |         1.12 MiB |                           0.22 MiB |
| 영상 검색 1채널·2,400개 영상              |         3.84 MiB |                           0.22 MiB |
| 영상 검색 8채널·19,200개 영상             |        28.89 MiB |                           0.22 MiB |
| 방송 통계 원본 페이지 60개·1,800행        |         1.22 MiB |                           0.24 MiB |
| 방송 통계 페이지 캐시 상한 960개·28,800행 |        15.54 MiB |                           0.29 MiB |

영상 검색 결과에는 댓글을 채우지 않았다. 실제 응답 크기와 댓글 길이에 따라 달라진다. 방송 통계의 페이지들을 병렬로 채운 것은 캐시 보유량을 보기 위한 시험이며, 실제 통계 UI의 순차 조회 성능이나 소요 시간으로 해석하지 않는다. 명시적으로 캐시를 비우면 대부분 반환됐지만, 사용자가 검색어를 지우는 동작은 캐시 비우기와 다르다.

채팅은 jsdom으로 100개·200개 모아보기와 2,000건 연속 입력을 시험했다. 보관 개수는 설정한 100/200개를 유지했다. 초기 대비 힙 증가는 각각 5.61/6.95/7.60 MiB였지만 jsdom의 스타일·DOM·선택자 캐시가 포함되므로 실제 Chrome 점유량으로 제시하지 않는다. 메시지 store를 정리할 때 반환된 힙은 100개 약 0.33 MiB, 200개 약 0.69 MiB, 2,000건 입력 뒤 100개 보관 약 0.35 MiB였다. 패널 렌더링과 전체 observer 처리는 이 시험에서 제외했다.

데이터 처리 CPU 시간은 영상 2,400개 인덱싱 중앙값 31ms, 19,200개 234ms였다. 이것은 한 번의 데이터 구축 CPU 누적 시간이며 실시간 CPU 점유율이 아니다. 짧은 작업은 Windows CPU 시간 해상도에 영향을 받아 0으로 기록되기도 한다. 채팅 jsdom 처리 시간은 Chromium 처리 시간으로 환산하지 않았다.

## 코드에서 확인한 부하 요인

1. **멀티뷰:** 보조 방송마다 별도 video/HLS 인스턴스가 생긴다. 설정은 forward buffer 30초, back buffer 60초이며 실제 버퍼 양은 스트림과 재생 상태에 따라 달라진다. 영상 디코딩·미디어 버퍼는 데이터 캐시 벤치마크에 포함되지 않는다. 여러 영상과 탭을 함께 여는 사용법이 우선적인 측정·조절 대상이다.
2. **영상 검색:** 기본 조회 범위는 80페이지, 요청 페이지 크기는 30개, 채널 캐시는 8개다. API가 요청 크기를 지킬 때 채널당 2,400개, 여러 채널을 순회하면 19,200개 인덱스를 보유할 수 있다. 댓글 조회 상한 60개는 검색 실행당 상한이므로 여러 검색을 거치면 더 많은 영상에 댓글이 누적될 수 있다.
3. **통계 캐시:** 채널 페이지 캐시는 8채널×120페이지이고 상세 응답 캐시는 600개다. 실제 월/기간 경계에서 일찍 멈추는 경우가 많아 매번 상한까지 채워지는 것은 아니다.
4. **TTL은 즉시 해제 타이머가 아니다:** 검색 5분, 통계 10분의 만료는 다시 접근할 때 검사한다. 오래된 캐시는 유휴 상태에서 시간만 지났다고 바로 메모리에서 사라지지 않는다. 필요하면 유휴 캐시 정리 정책을 검토할 가치가 있다.
5. **일반 시청:** 활성 조건에 따라 타임시프트 500ms, 일시정지 위치/지연 표시 1초, 시청 기록 확인 5초·저장 15초, 팔로잉 갱신 기본 30초 타이머가 있다. 각각의 작업량과 실행 조건이 다르므로 타이머 개수만으로 CPU를 계산할 수 없다. 채팅·DOM mutation의 빈도도 영향을 준다.
6. **초기 로드:** manifest에 등록된 콘텐츠 JS는 MAIN 7개 약 106 KiB, isolated 57개 약 1,798 KiB(그중 HLS 약 346 KiB)다. 이것은 파일 크기이며 RAM 사용량이 아니다. 모듈을 나눈 파일 수나 코드 줄 수만으로 부하를 판단할 수 없다.

## 판단과 다음 측정

일반적인 데이터 캐시가 수십 MiB를 사용할 가능성은 있지만, 이번 실측에서 나타난 브라우저 전체 수 GiB를 확장 코드나 캐시 때문이라고 볼 근거는 없다. 멀티뷰의 영상 수·해상도·버퍼가 더 큰 부하 변수가 될 수 있다. 작은 코드 줄이기보다 이 항목과 유휴 캐시 수명을 먼저 살펴보는 것이 합리적이다.

확장 순증분을 확정하려면 다른 탭의 재생을 멈춘 별도 프로필에서 같은 방송·화질·창 크기로 확장 OFF/ON을 번갈아 측정해야 한다. 1/2/3/6개 방송별로 충분히 예열하고 5~10분 표본, 힙 스냅샷, media/GPU 메모리와 드롭 프레임을 수집해야 한다. 장시간 누수 여부는 이번 짧은 표본으로 결론 내리지 않았다.

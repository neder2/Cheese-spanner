# 방송 목록 검색·필터 시간 비교

이 문서는 구현 전 비교용 코드의 측정 기록이다. 이후 적용한 썸네일·카드 생성·스크롤 개선의 검증은 [구현 검증 문서](category-tools-loading-verification.md)를 참고한다.

## 측정 범위 — 2026-09-12 KST

- 작업 branch: `1.3.6`, HEAD: `a2d83eb` (`Better Chzzk 1.3.5`). manifest/package 버전은 둘 다 `1.3.5`였다.
- 비교 기준은 커밋된 HEAD가 아니라 기존 미커밋 변경을 포함한 작업 파일이다. 방송 수 집계 기능도 포함했다.
- 실제 확장 코드는 수정하지 않았다. 기존 소스를 JSDOM에 로드할 때만 제안한 변경을 적용한 비교용 복사본을 만들었다.
- 이번 비교는 **결과 표시와 팔로워 배지 조회 분리**, **팔로워 전용 API 사용**만 대상으로 한다. 목록 수집 큐와 카드 렌더링 범위를 바꾸는 제안은 구현하거나 측정하지 않았다.
- 원본 수치와 소스 SHA-256은 [측정 자료](category-tools-performance-samples.json)에 보관했다.

## 실제 API 응답 시간

전체 방송 API에서 확인한 동일한 12개 채널에 두 endpoint를 각각 4번 호출했다. 연결 준비와 endpoint별 첫 호출을 제외하고, 채널마다 호출 순서를 번갈아 바꿨다. 비로그인 PowerShell `Invoke-WebRequest` 측정이며, 채널 쌍 사이에는 60ms 간격을 뒀다.

- 목록: `GET https://api.chzzk.naver.com/service/v1/lives?size=50`
- 기존: `GET https://api.chzzk.naver.com/service/v1/channels/{channelId}`
- 변경 후보: `GET https://api.chzzk.naver.com/service/v1/channels/{channelId}/followers/count`

| 항목                |   기존 채널 API | 팔로워 전용 API |
| ------------------- | --------------: | --------------: |
| 표본 수             |            48회 |            48회 |
| 중앙값              |         25.68ms |         20.89ms |
| 90백분위            |         34.11ms |         25.44ms |
| 최소 ~ 최대         | 17.31 ~ 38.29ms | 16.41 ~ 34.65ms |
| 평균 응답 본문 크기 |    755.25바이트 |     61.42바이트 |

48쌍 모두 HTTP 200이었고 `followerCount`가 일치했다. 응답 크기는 약 92% 줄었지만, 응답 시간 중앙값 차이는 약 4.79ms(19%)였다. 단일 호출의 연결 준비 시간이나 응답 크기 비율을 그대로 속도 향상으로 해석하지 않는다.

## 기존 소스와 비교용 코드

실제 목록에서 확보한 방송 12개와 위 API 지연 표본을 동일하게 재생했다. 기존 테스트의 목록 DOM fixture를 사용하고, 실제 `applyTools()` 및 repository를 실행했다. 각 조건·방식은 준비 실행을 제외하고 4번씩 비교했으며 실행 순서는 번갈아 바꿨다. Node는 `v24.18.0`이었다.

- 기본 설정 유지: 팔로워 6개씩, 동시 요청 2개, 묶음 사이 700ms.
- 검색 조건: 표본 중 방송 하나에만 일치하는 실제 채널명.
- 팔로워 필터 조건: 최소 1명. 실제 표본 12개 모두 통과하는 조건이다.
- 기존 방식은 검색 후에도 전체 카드 행에 대해 팔로워 조회 한 묶음을 기다린 다음 결과 수와 숨김 상태를 갱신한다.
- 비교용 코드는 팔로워 필터가 없을 때 결과를 먼저 갱신하고, 보이는 결과 중 화면 근처의 팔로워 배지만 나중에 조회한다. 팔로워 필터가 있으면 기존의 판정 대기를 유지한다.
- 초기 목록 응답 지연은 동일하게 305.48ms를 재생했다. 이는 해당 수집 실행의 첫 페이지 실측값이며 일반적인 목록 API 응답 시간으로 간주하지 않는다.
- 첫 결과 시간은 준비된 툴바에서 `applyTools()`를 호출한 시점부터 결과 수가 갱신되는 시점까지다.
- 검색 완료는 검색 결과에 필요한 팔로워 수까지 준비된 시점, 팔로워 필터 완료는 12개 모두의 팔로워 값과 표시 결과가 준비된 시점이다.
- 모든 실행에서 두 방식의 최종 표시 방송 ID가 같은지 assertion으로 확인했다. 검색 결과는 1개, 팔로워 필터 결과는 12개였다.

다음 값은 각 4회 실행의 중앙값이다.

| 조건                                 | 지표                       |       기존 | 비교용 코드 | 해석                  |
| ------------------------------------ | -------------------------- | ---------: | ----------: | --------------------- |
| 목록은 확보, 팔로워 캐시는 비어 있음 | 검색 첫 결과               |   146.27ms |     43.52ms | 약 102.75ms 단축      |
| 초기 목록 조회 포함, 캐시 비어 있음  | 검색 첫 결과               |   467.93ms |    361.35ms | 약 106.58ms 단축      |
| 초기 목록 조회 포함, 캐시 비어 있음  | 검색 결과 팔로워까지 완료  |   476.91ms |    419.32ms | 약 57.59ms 단축       |
| 초기 목록 조회 포함, 캐시 비어 있음  | 팔로워 필터 첫 결과        |   465.88ms |    452.92ms | 약 12.96ms 차이       |
| 초기 목록 조회 포함, 캐시 비어 있음  | 팔로워 필터 12개 판정 완료 | 1,252.22ms |  1,244.38ms | 실질적인 큰 차이 없음 |
| 목록·팔로워 캐시 모두 확보           | 검색 첫 결과               |    38.04ms |     47.56ms | 개선 확인 안 됨       |
| 목록·팔로워 캐시 모두 확보           | 팔로워 필터 첫 결과        |    38.46ms |     38.74ms | 거의 같음             |

팔로워 캐시가 없는 좁은 검색에서는 팔로워 요청이 기존 6회에서 비교용 코드 1회로 줄었다. 팔로워 필터 조건에서는 두 방식 모두 12회였고, 캐시가 있는 조건에서는 둘 다 추가 팔로워 요청이 없었다.

## 해석과 한계

이번 표본에서는 검색 첫 결과의 불필요한 대기를 없애는 효과가 가장 컸다. 팔로워 전용 API로 바꾸는 것만으로 팔로워 필터 전체가 크게 빨라지지는 않았다. 6개씩 처리한 뒤 기다리는 700ms 간격과 채널별 요청 수가 그대로 남기 때문이다.

캐시가 있는 검색의 실행 범위는 기존 36.3~53.7ms, 비교용 코드 38.1~56.4ms였다. 이 조건에서는 속도 개선이 관측되지 않았고, 수 ms 차이를 안정적인 성능 차이로 단정하지 않는다.

이 결과는 **실측 API 지연을 재생한 JSDOM 소스 비교**다. 실제 Chrome 확장 화면의 체감 시간이나 전체 방송 목록의 완료 시간이 아니다. 키 입력 debounce, 스케줄러 대기, 실제 CSS 레이아웃·화면 그리기, 이미지 로딩, React 재렌더, 무한 스크롤과 다수 카드 생성은 포함하지 않았다. 표본은 하나의 12개 목록으로 한정했고, fixture의 다음 페이지는 없음으로 설정했다. 수백 개 방송으로 그대로 외삽하지 않는다.

기능 변경을 완료한 것이 아니므로 전체 런타임 테스트·실브라우저 스모크는 수행하지 않았다. 실제 확장 적용 후에는 같은 계정·목록·캐시 상태에서 첫 결과와 필터 완료 시간을 다시 측정해야 한다.

# 1.3.7 라이브 첫 재생·720p 선택 조사

## 범위와 관측

2026-09-14, 브랜치 `1.3.7`, HEAD `b2f22a2b6e36ea3c1402c3b22580b3f644c3f4a2`에서 작업했어요. 사용자가 새로고침 후 한 번 재생 버튼을 눌러야 했던 현상과 720p 고정 시 480p로 남는 현상을 보고했어요. 버전은 유지하며 커밋·push·릴리스는 수행하지 않았어요.

현재 사용자 라이브는 `https://chzzk.naver.com/live/feb20a676694b1163fed010da0848303`였어요. 첫 읽기에서 자동 닫기 활성·누적 클릭 시도 5회, 안내 0개, 실제 1920×1080, paused false, readyState 4를 확인했어요. UI에는 1080p·720p·480p·360p가 있었고 확장 목표 화질은 1080p였어요. 이로써 이전에 추가한 안내 닫기 모듈의 실제 주입과 동작을 확인했어요.

같은 페이지를 새로고침하자 안내 닫기 시도 2회 후 안내가 사라졌지만, 실제 영상은 1920×1080 / readyState 4 / paused true / currentTime 28.015962로 남았어요. 당시 자동 화질 요청은 `1789381318774:7`, 결과는 `already`였어요. 재생 준비와 재생 진행이 서로 다를 수 있다는 실제 사례예요. 캡처된 warn/error 로그는 없었고, 특정 play Promise의 오류명까지 수집하지는 않았어요.

## 720p 원인과 수정

현재 공식 [live-detail 응답](https://api.chzzk.naver.com/service/v3/channels/feb20a676694b1163fed010da0848303/live-detail)을 2026-09-14 10:22:25 UTC에 읽었어요. code 200 / status OPEN, HLS·LLHLS 모두 아래 트랙을 포함했어요. 미디어 URL과 서명값은 기록하지 않아요.

| encodingTrackId | 크기      | FPS | p2pPath 존재 |
| --------------- | --------- | --- | ------------ |
| 1080p           | 1920×1080 | 60  | 있음         |
| 720p            | 1280×720  | 60  | 있음         |
| 480p            | 852×480   | 30  | 없음         |
| 360p            | 640×360   | 30  | 없음         |

이전 구현은 취소 결과를 유지하는 조건을 1080p 하나로 제한했어요. 720p 트랙은 실제로 제공되지만 미설치 취소 분기를 통과하지 못하고, 기존 480p 선택이 남을 수 있었어요. 실측한 1280×720 / encodingTrackId 720p / low-latency 조합을 추가했어요. 1080p가 없는 경우 자동 화질이 선택한 720p 하위 트랙도 같은 네이티브 경로로 처리해요. 다른 크기·종류·encodingTrackId, 수동 선택의 다른 목표 화질, 다른 이벤트와 원래 반환값은 변경하지 않아요.

## 첫 재생과 화질 변경의 순서

실제 페이지가 사용한 엔트리는 [index-GNyFfAPg.js](https://ssl.pstatic.net/static/nng/glive/resource/p/static/js/index-GNyFfAPg.js)였어요. 소스를 데이터로 읽어 다음 흐름을 확인했어요.

- `JY`의 loadedmetadata 처리에서 `CY`를 호출하고, `CY`는 저장된 화질·사용 가능한 화질을 반영한 후 `Vf`를 호출해요.
- `Vf`는 원래 플레이어의 play를 요청하고, AbortError인 경우 재시도하지 않아요.
- [player-vendor-BYg0wCyN.js](https://ssl.pstatic.net/static/nng/glive/resource/p/static/js/player-vendor-BYg0wCyN.js)의 선택 액션(34727)은 트랙의 selected를 변경해요. 반환 Promise는 영상의 실제 재생 시작까지 보장하지 않아요.

확장의 이전 네이티브 경로는 첫 재생 전에 트랙이 노출되는 즉시 선택할 수 있었어요. 초기 play 요청과 트랙 변경이 겹치는 위험을 확인했지만, 위 실제 정지 사례가 AbortError로 발생했다는 직접 이벤트 로그는 없어요. 이전 일반 경로의 재생 복구 함수도 새 네이티브 경로에서는 호출되지 않았어요.

수정은 첫 재생 순서를 보장하는 데 한정했어요. 해당 영상에 실제 재생 이력(`played.length > 0`)이 없으면 자동 선택을 `native-playback-start`로 대기하고, 첫 playing 이벤트 후 화질 적용을 예약해요. 이미 재생했던 일시정지 영상은 화질을 바꿔도 일시정지를 유지해요. 설치 안내 닫기와 화질 메뉴의 원래 동작은 그대로 사용해요. 새 play 호출·음소거 변경·재시도 타이머는 추가하지 않았어요. 대기 리스너는 옵션 끄기·라우트/영상/provider 교체 때 정리해요.

[Chrome 자동 재생 정책](https://developer.chrome.com/blog/autoplay/)에 따른 제한이나 별도의 플레이어 오류까지 없어진다는 보장은 아니에요. 브라우저가 재생을 허용하지 않으면 사용자의 재생 입력이 필요할 수 있어요. 확장에서는 재생이 실제로 시작되기 전 화질 변경으로 초기화를 방해하지 않는 범위를 처리해요.

## 회귀 검사

수정 전 검사에서 720p 반복 선택·수동 선택·1080p 부재 시 720p 선택과 첫 재생 대기·대기 취소 등 6개 사례가 실패했어요. 수정 후 네이티브 화질 13개와 안내 닫기 10개, 합계 23개가 통과했어요. 기존 취소 방지 검사는 관측되지 않은 kind로 옮겨 계속 유지하며, 폭·encodingTrackId가 다른 트랙과 상위 화질 취소도 추가로 확인해요.

실제 수정본 검증을 위해 사용자에게 개발자 확장 다시 로드와 목표 화질 720p 저장을 요청했어요. 전체 검사와 새 브라우저 관측 결과는 아래에 이어 기록해요.

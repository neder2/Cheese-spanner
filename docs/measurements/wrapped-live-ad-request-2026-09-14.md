# 감싸진 라이브 광고 요청의 보수적 처리 (2026-09-14)

    - [플레이어 SDK](https://ssl.pstatic.net/static/nng/glive/resource/p/static/js/player-vendor-BYg0wCyN.js): SHA-256 `3add7ef97995bc4e7052e03c84c18e9fe34d5d6212e4672c6f5f76412c9147bc`.
- 이번 근거는 배포 클라이언트 코드다. 로그인된 탭의 해당 분기 실행이나 광고 응답을 캡처한 자료는 아니다.

## 확인한 계약

라이브 호출부는 파싱된 `livePlaybackJson`이 존재하고 그 `meta.liveId`가 현재 `liveId.toString()`과 다르면, 라이브 광고 요청을 `NLiveCastAdRequest`로 감싸 `adsController.srcObject`에 연결한다. 생성 시 `linearAdRequest`와 `playerType: "LIVE_PW"`를 전달한다.

래퍼 생성자의 `Constants.NLIVECAST_ID`는 `ncast.advertisement`다. 생성된 `_init`에는 `playerType`, `uiElements`, `disableTrackingCors`, `linearAdRequest` 네 필드가 있다. 기본 UI 값은 `uiClickThrough`이며, 광고 요청은 `LIVE_CHZZK_NDP_SCH` 또는 `LIVE_CHZZK_NDP_SCH_EVENT`와 `svc: "chzzk_live"`로 설정된다.

래퍼의 `initAd`는 내부 요청이 있으면 그 초기화를 호출한다. 내부 요청이 없거나 그 초기화가 실패해도 바깥 클라이언트를 생성한다. 바깥 클라이언트는 본영상의 메타데이터·재생·탐색 상태와 광고 이벤트를 연결하므로 래퍼 전체를 제거하지 않는다.

## 구현 범위

- 기존 `srcObject` setter가 정상적으로 반환한 뒤 해당 래퍼의 내부 요청 전달만 처리한다. 바깥 객체, `_init` 객체, 원래 메서드와 내부 요청 객체는 유지한다.
- 라이브 경로, 광고 컨트롤러 메서드, 실제 연결된 `.chzzk_player` 하위 영상, 생성자 상수와 프로토타입, 확인한 네 설정 필드가 모두 맞아야 한다.
- 내부 요청 자체도 기존 라이브 광고 스케줄 ID와 서비스 값에 일치해야 한다. 광고 ID만으로 감싼 객체 전체를 차단하지 않는다.
- 변경 가능하고 쓰기 가능한 자체 데이터 필드에만 접근자를 설치한다. 알 수 없는 추가 필드, 다른 서비스·스케줄·플레이어, 외부 접근자와 읽기 전용 설정은 그대로 통과한다.
- SDK가 내부 요청을 읽을 때 현재 경로·설정·플레이어 연결·소스 정체성·요청 내용을 다시 확인한다. 일치하는 동안만 내부 요청 대신 `null`을 반환한다. 원래 SDK의 선택적 요청 초기화 경로를 사용하며 완료 이벤트를 만들지 않는다.
- 옵션을 끄거나 조건이 달라지면 원래 요청을 반환한다. 요청 교체도 보존하며, 같은 래퍼를 새 플레이어에 연결하면 소유 컨트롤러를 갱신한다. 기존 규칙대로 같은 문서에서 껐다 다시 켜면 새로고침이 필요하다.
- WeakMap은 살아 있는 래퍼의 중복 설치를 구분한다. 별도 강한 참조 목록, 타이머, 네트워크 요청, 전체 DOM 검색을 추가하지 않는다.
- 방송 스트림 자체에 포함된 광고는 변경하지 않는다.

## 진단 정보

`data-betterchzzk-ad-video-status`의 `blockedWrappedLiveRequests`는 일치한 내부 요청의 읽기를 `null`로 처리한 횟수다. 원래 SDK 초기화 경로는 이 필드를 한 번 읽지만, 다른 코드가 직접 읽어도 횟수에 포함될 수 있다. 실제 광고 배정 수나 광고 차단 성공 수가 아니다. 바깥 소스를 유지하므로 `blockedLiveSources`와 구분한다.

이 값은 현재 문서의 DOM에만 표시하고 저장·전송하지 않는다. 새 문서에서는 0으로 시작한다. 해당 처리 후 옵션을 끄면 기존 다른 광고 처리와 마찬가지로 새로고침 필요 상태를 표시한다.

## 검증 근거와 한계

- 구현 전에 정상적인 내부 광고 요청이 그대로 초기화되는 실패를 재현했다. 이후 추가한 네 회귀 테스트와 기존 광고 테스트를 통과했다.
- 관련 검사 58개와 `npm.cmd run test:all`의 전체 612개가 통과했다. `npm.cmd run lint`, `npm.cmd run format:check`, `git diff --check`도 통과했다.
- 확인한 일반·이벤트 스케줄, 바깥 객체·메서드 동일성, 반복 연결 시 중복 방지, 미확인 구조 통과, 페이지 이동, 영상 분리·재마운트, 소스 소유권 변경, 내부 요청 교체, 옵션 해제와 재활성화 대기를 검사했다.
- 배포 SDK의 원본 `NLiveCastAdRequest` 클래스만 제어된 VM에서 분리해 확인했다. 활성 상태에서는 내부 요청 호출 0회와 바깥 클라이언트 생성 유지, 비활성 상태에서는 원래 내부 요청 호출 1회, 잘못된 인자 검증 및 내부 요청 실패 처리 보존을 확인했다. 바깥 클라이언트는 생성 인자를 기록하는 대역으로 바꿨으므로 실제 메타데이터 처리나 영상 재생까지 검증한 결과가 아니다. 이 분리 검증의 원격 SDK 코드는 확장 패키지나 테스트에 포함하지 않았다.
- 실제 브라우저에서 확장 재로드·주입, 해당 광고 배정, 타임머신·PiP·채널 이동 후 재생은 미검증이다. 일반 라이브에서 이 분기가 발생하지 않으면 이 수정의 실제 차단 효과를 확인한 것으로 볼 수 없다.

수동 확인 시 확장을 다시 로드하고 치지직 탭을 새로고침한다. 실제 확장 ID, 옵션 상태와 새 진단 필드로 수정본 주입을 확인한 뒤 라이브 재생·채널 이동·타임머신·PiP와 옵션 해제를 확인한다. 해당 요청 분기에서 내부 요청 처리 횟수가 늘더라도 본영상의 정상 재생과 콘솔 오류 유무를 별도로 확인해야 한다.

# 확인형 안내 자동 닫기 — 2026-10-11

상태: **구현 완료 · 사용자 실제 환경 확인(자동 닫기·단축키 정상, 결과 `removed`).** 안내 DOM 실측은 [확인형 안내 실측](adblock-notice-confirm-2026-10-11.md)에 있어요.

## 1. 배경

- 일부 환경에서 라이브·다시보기에 들어갈 때 버튼이 **확인** 하나뿐인 안내(`data-nlog-area="ad_blocking_info_layer"`)가 떠요. 기존 `시청 방해 팝업 제거`는 이름이 `닫기`인 버튼만 눌러서 이 안내는 남았어요.
- 2026-10-11 사용자가 같은 옵션으로 이 안내도 닫도록 요청했어요.
- 검토한 대안과 결론:
    - 스크립트 클릭: 확인 버튼이 반응하지 않아 쓸 수 없어요.
    - CSS로 숨기기: 모달의 스크롤 잠금·단축키 차단 정리가 일어나지 않아요(1.3.9에서 버린 방식).
    - 새 권한이 필요한 방식: 최소 권한 원칙 밖이라 쓰지 않아요.
    - 결론: 확인 버튼에 연결된 현재 확인 동작을 한 번 실행하고, 치지직이 안내를 직접 제거하게 해요.

## 2. 구현 계약

- 역할: isolated `features/adblockPopup.js`가 옵션·관찰·표시 주기·한도를 소유하고, MAIN `features/adblockPopupPage.js`는 요청을 받았을 때만 대상을 다시 확인하고 실행해요.
- 대상 판단: 저장 옵션 최초 읽기 뒤 ON, 경로 `/live/{id}` 또는 `/video/{숫자}`일 때만 다뤄요. 이 안내는 표시·크기가 아니라 다음 조건으로 판단하며, 일반 닫기 경로의 가시성 필터보다 먼저 분기해요.
    - 현재 문서에 연결된 `[role=alertdialog][aria-modal=true][data-nlog-area=ad_blocking_info_layer]`가 문서에 하나뿐이에요.
    - body 직속 `_dimmed_` 배경의 유일한 자식이고, 안에 다른 대화상자가 없어요.
    - 실측한 제목·본문, 도움말 링크 하나가 있어요.
    - 안내 안에 비활성이 아닌 `type=button` `확인` 버튼이 하나뿐이에요.
- MAIN 확인: 위 조건을 다시 보고, 버튼과 안내 노드의 현재 React props(`__reactProps$*`) 키가 각각 하나이며 서로 같은지 확인해요. 안내 props의 `role`·`data-nlog-area`, 버튼 props의 `type`·비활성 여부, `onClick`이 실측한 확인 함수 형태인지도 봐요. 조건이 맞을 때만 실측한 최소 인자로 한 번 실행하고, 같은 버튼의 재요청은 거절해요. 번들 축약 이름·접미사·hook 순번은 쓰지 않아요.
- 흐름: 대상 확인 → 안내와 그 배경만 임시 숨김 → MAIN 동기 요청으로 한 번 실행 → 안내 노드의 실제 연결 해제 관찰. 실행 반환이나 숨김은 성공으로 보지 않고, 스크롤·단축키 정리는 치지직(React)에 맡겨요.
- 대기와 실패: 실제 제거까지 숨김을 유지하되 최대 `NOTICE_REMOVAL_WAIT_MS = 1000`ms예요. MAIN 거절·실행 예외·보조 스크립트 누락은 즉시, 시간 초과는 1초 뒤 숨김만 풀어 직접 확인할 수 있게 해요. 실패한 안내는 다시 숨기거나 다시 실행하지 않아요.
- 한도: 같은 표시 주기·같은 버튼 노드에 한 번만 실행해요. 같은 경로에서 두 번 닫은 뒤 다시 뜬 안내는 남겨요(한 번 입장에서 서로 다른 두 경로로 각각 뜰 수 있어 2회). 경로가 바뀔 때만 한도를 초기화하고 옵션 OFF/ON은 초기화하지 않아요.
- 정리: OFF·라우트 변경·`pagehide`(BFCache 포함)는 대기를 끝내고 숨김을 풀어요. 늦은 타이머는 같은 대기·세대일 때만 동작해요. 버튼 교체로 끝난 대기는 성공으로 세지 않아요. 일반 닫기 경로의 다음 프레임 복원은 대기 중인 안내를 건드리지 않아요.
- 첫 화면: 설정 ON 확인 즉시 패키지 내 숨김 스타일을 준비해요. 선택자만으로 미리 가리는 CSS는 쓰지 않고, 검증한 노드에만 속성을 붙여요. 설정 미확인·OFF에서는 숨기지 않아요. 설정을 읽기 전에 그려진 프레임은 막지 못해요.
- 진단 속성: `data-betterchzzk-adblock-notice-confirm`(MAIN 실행·거절 횟수), `data-betterchzzk-adblock-notice-result`(마지막 결과 `removed`·`timeout`·`refused`·`replaced`·`hidden`·`cancelled`, 대기 ms, 횟수).
- 하지 않는 것: 새 권한, `Event.prototype`·전역 React 패치, 재생·화질·응답 데이터 변경, `body` 스크롤 강제 해제, DOM 강제 제거, 반복 타이머·재시도, 원격 코드, 페이지가 보낸 함수명·선택자·코드 실행.
- 페이지도 같은 요청 이벤트를 보낼 수 있지만, MAIN은 같은 검증을 통과한 페이지 자신의 확인 동작만 실행해요. 확장 저장소·특권 API·네트워크로 이어지지 않아요.
- 기존 `닫기` 버튼 경로와 고화질 설치 안내 처리는 그대로예요.

## 3. 공개 코드 근거 — 정적 분석

라이브 HTML이 참조한 파일을 실행하지 않고 읽었어요. 엔트리 `index-VdvK-ysl.js`(SHA-256 `895aa5e054f7a80936db80d47fb20cb98485657d3ddad1a752fdce8ea6778668`), `common-vendor-pcHQV1G2.js`(`2801491c851815a10c8f5afcbbbd448fbd861e6e3b690adcd3cb8f1cda1ccea0`), `strings-ko_kr.json`(`ef508a98b148401595e1c25969ba1094aae1128fe2896147b447183b4f6b0c07`)이에요.

- 안내는 공용 모달의 footer `buttonList[0].clickHandler`로 확인 동작을 넘기고, 버튼 컴포넌트가 이를 `<button onClick>`으로 그대로 연결해요. 버튼의 현재 `onClick`이 확인 동작 자체예요.
- 확인 동작은 안내 표시 상태 하나만 꺼요. 라이브·다시보기 모두 같은 형태예요. 재생·화질 상태는 바꾸지 않아요.
- 공용 모달은 표시 중 단축키 차단과 `body` 스크롤 잠금을 켜고, 사라질 때의 effect 정리에서 풀어요.
- React 18.3.1이며 DOM 노드 키는 `__reactProps$` + 임의 접미사예요.
- 별도로 `popup.close` 문구가 `팝업 닫기`여서 기존 `닫기` 경로와 다르다는 점을 [남은 확인](../tracking/findings.md)에 기록했어요.

## 4. 자동 검사

- `tests/adblock-notice-confirm.test.js` 28개가 MAIN과 isolated를 같은 JSDOM에 연결해 검사해요. 정확 대상만 1회, 표시되지 않거나 크기 0인 정확 대상 처리, 비대상·모호·비활성·연결 해제·템플릿·숨김 속성만 있는 노드 거절, React 연결 없음·충돌·교체·예외, 늦은 제거 동안 숨김 유지와 1초 복원, 저장 설정 대기·OFF·SPA·`pagehide`·늦은 타이머, 경로당 한도, 다른 팝업·입력 초점 보존을 포함해요.
- 첫 구현은 수정 전 코드에서 13개가 실패했어요. 가드를 하나씩 뺀 변이는 첫 구현에서 13종 모두, 깜빡임 보완에서 13종 중 11종이 단독으로 테스트 실패를 냈어요. 남은 2종은 다른 방어가 같은 동작을 보장하는 이중 방어여서, 두 방어를 함께 뺐을 때 실패하는 것을 확인했어요.
- `adblock-popup-close` 20개와 전체 `test:all`·`lint`·`format:check`가 통과했어요. JSDOM 모형은 실제 React 렌더를 재현하지 않아요.

## 5. 화면 확인 — Edge 155.0.4283.45 임시 프로필 + CDP

사용자 프로필·로그인은 쓰지 않았고 측정 뒤 임시 프로필 프로세스만 종료했어요. 대상은 `/live/b044e3a3b9259246bc92e863e7d3f3b8`이에요.

### 5.1 구현 직후(16:00 KST 무렵)

- 확장 주입과 world 분리, 실제 치지직 버튼의 단일 `__reactProps$*` 키를 확인했어요. 실제 공용 모달(`로그인이 필요한 서비스`)에서 컨테이너·footer 버튼이 같은 키를 쓰고 버튼 `onClick`이 footer의 clickHandler와 같은 것을 읽기 전용으로 확인했어요. 같은 모달에서 신뢰 입력 M 키는 표시 중 무시되고 정상으로 닫힌 뒤 동작했어요.
- 실측 구조의 합성 안내로 확장 isolated → MAIN 동기 요청과 경로당 2회 한도, 입력 초점·입력값 유지, 1080p 본영상 진행을 확인했어요. 스크립트 `click()`은 확인 동작을 실행하지 못했어요.
- 측정 도구 결함: 첫 합성 실행의 제거 코드가 열려 있던 로그인 모달의 `body` 스크롤 잠금을 풀었어요. 확장 동작이 아니라 측정 코드 문제이며 다음 실행에서 고쳤어요.

### 5.2 입장 깜빡임(16:20~16:40 KST)

- 보고: 사용자가 실제 환경에서 자동 닫기·단축키 정상을 확인하고, 입장 때 약 0.1초 보인다고 했어요(체감값).
- 방법: 임시 프로필에서 안내가 표시되는 조건을 만들어 실제 안내를 띄우고, 삽입·숨김·제거 시각과 매 프레임의 그려질 상태(rAF·레이아웃 뒤, 페인트 직전의 ResizeObserver 콜백)를 기록했어요. 이 조건은 사용자 환경과 표시 경로가 달라요.
- 수정 전 3회(페이지 기준 ms):

| 회차 | 설정 준비 | 안내 삽입 | 실행·숨김 | rAF 복원 | 보이는 프레임 | 안내 제거 |
| ---- | --------- | --------- | --------- | -------- | ------------- | --------- |
| 1    | 117.8     | 2046.0    | 2049.1    | 2050.5   | 2051.2 (1개)  | 2053.0    |
| 2    | —         | 1878.7    | 1881.4    | 1882.4   | 1883.0 (1개)  | 1884.9    |
| 3    | —         | 1720.1    | 1722.4    | 1723.4   | 1723.7 (1개)  | 1724.9    |

- 원인: 숨김은 첫 프레임 전에 적용됐지만 조건 없는 단일 rAF 복원이 안내 제거(실행 후 2.5~3.9ms)보다 먼저 와서 한 프레임 다시 그려졌어요. 설정 읽기 전 표시나 재표시는 아니었어요. 사용자 체감 0.1초는 사용자 환경에서 제거가 더 늦었던 경우로 추정해요.
- 보완 후 같은 조건 3회: 보이는 프레임 0개, 결과 `removed`(대기 3~5ms). 미리 입력해 둔 검색창의 초점·입력값이 유지되고 `body` 스크롤 잠금은 React가 풀었어요.
- 확장 없이 같은 조건에서 직접 확인을 눌러도 본영상이 시작되지 않았어요. 이 측정 조건의 사이트 동작이며 확장과 무관해요. 같은 이유로 이 조건에서는 M 키를 확인할 수 없었어요.

### 5.3 사용자 확인

- 보완본 적용 뒤 실제 환경의 결과 속성: `{"last":"removed","waitMs":2,"removed":1,"timedOut":0,"refused":0}`.
- 1.4.3 릴리스 전 실제 Chrome 점검을 사용자가 "정상"으로 보고했어요([1.4.3 검증 기록](../release-1.4.3-verification.md)).

## 6. 남은 확인

- 사용자 환경에서 깜빡임이 눈으로도 사라졌는지는 별도 보고를 받지 않았어요.
- 설정을 읽기 전에 안내가 먼저 그려지는 경우는 막지 못해요.
- 확인 절차: 확장을 다시 로드하고 치지직 탭을 새로고침한 뒤 안내가 뜨는 환경에서 라이브·다시보기에 들어가요. 콘솔에서 `document.documentElement.getAttribute("data-betterchzzk-adblock-notice-result")`를 실행해 `last`·`waitMs`를 기록하고, 단축키·채팅 입력·본영상 진행을 확인해요. 옵션을 끄면 안내가 남는지, 같은 방송에서 세 번째로 뜨면 남는지도 확인해요.

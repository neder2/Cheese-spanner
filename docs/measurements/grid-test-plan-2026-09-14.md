## 실측 순서

1. 사용자 브라우저에서 Better Chzzk, 광고 차단, UA 변경 등 재생에 영향을 줄 확장을 잠시 끄고 같은 방송을 새로고침해요. 실제 브라우저와 로그인 상태를 유지해 비교해요.
2. 원래 상태에서 1080p를 선택해 영상 해상도, 설치 안내, 광고 차단 안내를 기록해요. 광고 차단에 따른 화질 제한이 보이면 그리드 실험과 구분해요.
3. [읽기 전용 진단 코드](quality-choice-preflight-2026-09-14.js)를 Console에서 실행해 실제 플레이어 구조와 기존 개입 여부를 확인해요. 표시는 일부 지표일 뿐 모든 확장의 부재를 증명하지 않아요.
4. 관측된 플레이어의 해당 화질 선택 이벤트에 한정해, 한 번의 선택 취소만 억제하는 임시 실험을 준비해요. 실제 이벤트 경로 확인 전에는 기존 소스의 태그·이벤트 이름을 그대로 가정하지 않아요.
5. 취소 차단만 적용한 결과와 안내만 숨긴 결과를 분리하고, 필요하면 두 조건을 조합해요. 이후에 UA 후보를 별도 조건으로 확인해요.

성공 판정은 메뉴의 1080p 표시에만 의존하지 않아요. 실제 디코딩 해상도가 유지되는지, 재생 시간이 진행되는지, 장시간 재생과 새로고침·다른 방송에서도 같은지 확인해요. 그리드 사용 여부는 커넥터 프로세스·로컬 미디어 연결·전송 경로를 함께 봐야 해요. 순간적인 업로드 0이나 프로세스 미관측만으로 전체 구간의 미사용을 확정하지 않아요.

## 이번에 실제로 확인한 범위

사용자가 실측 가능하다고 알려준 뒤 브라우저 사용 도구만으로 Codex 내부 브라우저에서 홈을 열고, 진행 중인 한동숙 방송으로 이동했어요. 읽기 전용 DOM 조회에서 실제 영상은 640×360, 재생 중, readyState 4였어요. 동시에 광고 차단 안내가 표시됐고, Better Chzzk 그리드 상태·준비 마커는 없었어요.

이 환경은 광고 관련 제한의 영향을 분리할 수 없어서 사용자 브라우저 비교의 기준으로 채택하지 않았어요. 안내를 우회하거나 설정을 바꾸지 않았고 임시 탭을 닫았어요. 이 세션에서 관측한 엔트리는 `index-C4sif-4p.js`여서, 별도 HTTP 조사에서 확보한 `index-GNyFfAPg.js`와 파일명도 달랐어요.

사용자는 임시 스크립트를 개발자도구 Console에서 직접 실행할 수 있다고 답했어요. 이 단계에서는 읽기만 하는 사전 진단부터 제공했어요. 이후의 관측과 선택 허용 실험 결과는 아래에 기록해요.

### 반복 선택 문제와 복원 범위

사용자는 여러 차례 시도한 뒤 화질을 바꿔도 적용되지 않는다고 보고했어요. 첨부에는 그 후의 각 선택 시각·요청 트랙·반환값이 없어 모든 전환 실패의 원인은 아직 확인할 수 없어요.

이 코드는 지속적으로 화질을 허용하는 기능이 아니에요. 관측된 1080p / low-latency 선택에만 한 번 적용되고, 그 호출 안에서 원래 `$dispatch`를 복원해요. 이후 선택에는 원래 취소 처리가 다시 적용되며, 720p 등 다른 트랙은 허용 대상이 아니에요. 따라서 뒤따른 고화질 선택이 다시 취소되는 것은 코드의 적용 범위와 일치해요. 360p·480p까지 전환되지 않는 증상은 이것만으로 설명할 수 없어요.

확보한 공식 엔트리 `index-GNyFfAPg.js`에서 `dY`의 취소 처리도 `MR`을 호출하고, 설치 안내 `iX`의 ‘일반화질로 시청’ 콜백도 현재 선택된 트랙이 있으면 `MR`을 호출해요. `MR`은 `live-player-video-track`에 화질 label·width·height를 저장해요. 따라서 안내를 닫을 당시 선택이 1080p라면 그 값이 저장될 수 있어요. 해당 콜백 자체에는 480p 트랙을 직접 선택하는 호출이 없지만, 다른 상태 변화에 따른 후속 처리까지 없다는 뜻은 아니에요. 사용자 브라우저의 실제 저장값은 읽지 않았어요.

문제 분리를 위해 확장을 끈 상태로 같은 방송 탭을 새로고침하고, 코드를 다시 실행하지 않은 상태에서 일반 화질 간 전환을 확인하도록 안내했어요. 새로고침은 페이지 안 임시 메서드·타이머·관측을 제거하지만 사이트가 저장한 화질 선호값까지 삭제하지 않아요. 저장소 전체 삭제나 사용자 설정 변경은 하지 않았어요.

사용자는 이 절차 뒤 ‘360p·480p는 정상적으로 바뀌어요’라고 답했어요. 따라서 새로고침 후에도 일반 화질 전환 장애가 남아 있다는 증거는 없어요. 이 답변은 초기화 전 각각의 실패한 선택 원인이나 향후 고화질 반복 전환 성공을 확정하지는 않아요.

추가 로컬 JSDOM 모의 검사에서는 원래 함수가 480p 이하를 허용하고 고화질을 취소하는 조건으로 `1080p → 480p → 1080p`를 연속 호출했어요. 결과는 `true → true → false`였고 첫 호출 직후 원래 메서드와 속성 소유 상태가 복원됐어요. 다시 실험을 준비한 뒤 720p는 `false`, 1080p는 한 번 `true`였으며, 원래 함수는 모든 선택마다 호출됐어요. 이 검사는 실험 코드의 1회 적용·복원 동작에 대한 근거이고 실제 CDN 전송이나 브라우저 전환 성공의 추가 실측은 아니에요.

### 다음 단계: 3분 동안 반복 전환과 재생 진행 관측

사용자가 ‘그럼 이게 끝임?’이라고 이어서 확인을 요청했어요. 한 번의 성공을 최종 검증으로 취급하지 않고, [3분 세션 실험](quality-choice-session-2026-09-14.js)을 별도로 준비했어요. 기존 확장 런타임이나 manifest에는 추가하지 않았어요.

같은 한동숙 방송을 새로고침하고 Better Chzzk를 끈 조건에서 코드를 한 번 실행해요. `1080p → 480p → 1080p` 순서로 각각 10초 이상 관측하고, 팝업은 원래 ‘일반화질로 시청’ 버튼으로 닫아요. 마지막에는 1080p로 두고 3분 자동 종료 결과를 받아요. 첫 실험과 달리 팝업을 닫는 동작이 포함되므로 이 조건도 결과 해석에 반영해야 해요.

실험은 관측된 1920×1080 / low-latency / encodingTrackId 1080p 선택에만 원래 false 반환값을 true로 바꿔요. 480p의 원래 처리는 유지하고, 관측하지 않은 720p 허용이나 화질 자동 선택·팝업 자동 닫기는 추가하지 않았어요. 원래 함수와 부작용은 매번 실행돼요.

실행 식별자와 선택 순번, 선택 전·10초 뒤·실험 시작 60초·120초·종료 시점의 실제 영상 해상도·재생 시간·전체/누락 프레임 수를 기록해요. 다른 선택이 시작되면 이전 선택의 대기 중 관측을 취소해 로그가 잘못 연결되지 않게 해요. 리소스 관측은 앞선 실험과 같은 호스트 요약에 한정하며 전체 P2P 미사용 증명으로 취급하지 않아요. 경로·쿼리·인증값은 출력하지 않아요.

최대 3분·12회 선택으로 제한하고, 중복 붙여넣기로 세션을 겹쳐 설치하지 않아요. 시간 만료·수동 종료·탐지된 페이지/플레이어/provider 변경·원래 함수 예외 때 함수와 관측을 정리해요. SPA 변화는 선택·관측 시점과 popstate/hashchange/pagehide에서 확인하며 history API나 전역 이벤트 취소 메서드를 변경하지 않아요. 임시 코드 종료는 선택 화질·사이트 저장값의 초기화를 의미하지 않아요. 페이지 내 `bcQualityTrial.report()`는 중간 결과를 출력하고 `bcQualityTrial.stop()`은 종료 후 결과를 출력해요. 새 실험에는 새로고침이 필요해요.

[모의 검사](../../tests/evidence/quality-choice-session-probe.test.js)는 반복 선택, 원래 함수의 인자·반환값 보존, 관측되지 않은 트랙 제외, 중복 설치 방지, 시간/선택 횟수 제한, 페이지·provider 변경과 예외 정리, 속성 복원 및 다른 코드의 변경 보존, 리소스 호스트 경계와 URL 비출력을 확인해요. 사용자 브라우저의 3분 실측 결과는 다음 절에 기록해요.

# 방송 알림 전용 탭과 화면 등록 버튼

이 문서는 최초 개별 등록 버튼 구현과 발신 주소 검사 수정의 기록이다. 이후 사용자 요청으로 상단 통합 버튼·채널명 검색으로 변경했으며, 최종 동작과 브라우저 검증은 [상단 방송 알림 버튼 실측](live-start-header-search-2026-09-19.md)을 따른다.

## 범위

- 2026-09-19, `1.3.9` 브랜치의 `74ef00554537c5db926e4bf29de5583c28d96a05` 이후 작업이다. 기존 미공개 기획안은 수정하지 않았다.
- 사용자는 공개했던 1.3.9 릴리스를 초안으로 내린 뒤, 알림 설정의 전용 탭과 방송 화면 아래·채널 페이지의 등록 버튼을 요청했다.
- 버전·권한을 추가 변경하지 않고 기존 채널 목록과 알림·자동 열기 설정을 재사용한다. 이 구현 작업에서 커밋·태그·GitHub 릴리스 재게시를 하지 않는다.

## 현재 화면 구조 근거

- 당일 홈페이지가 참조하는 [index-DdGx9_UO.js](https://ssl.pstatic.net/static/nng/glive/resource/p/static/js/index-DdGx9_UO.js)의 React 구성과 [index-DGkZNTRv.css](https://ssl.pstatic.net/static/nng/glive/resource/p/static/css/index-DGkZNTRv.css)를 확인했다. 실제 탭의 DOM을 새로 수집한 결과와 구분한다.
- 라이브 하단 채널 정보는 `_inner_*` 안의 `_channel_*`와 `_control_*`로 구성되며, 공유 버튼은 `id="spi_button"`과 현재 페이지의 `data-url`을 가진다. 채널 링크와 공유 URL이 현재 라우트의 채널과 모두 일치할 때만 컨트롤 영역에 등록 버튼을 붙인다.
- 채널 페이지는 `_area_*` 아래의 `_information_*`에 h2와 `https://game.naver.com/profile/{channelId}` 링크를 두며, `_control_*`을 나란히 배치한다. 현재 채널의 프로필 링크와 해당 컨트롤을 함께 확인한다.
- 클래스 해시는 식별에 사용하지 않는다. 구조가 불명확하거나 대상 컨트롤이 둘 이상이면 버튼을 붙이지 않는다. 네이티브 노드를 이동·삭제하지 않고 확장 소유 요소만 추가한다.
- 현재 CSS의 `--sem-color-surface-neutral-*`, `--sem-color-content-neutral-primary`, `--sem-color-content-brand-strong`, `--sem-color-border-neutral-weak`를 확인하고 기존 대문자 토큰 및 정적 기본값을 함께 둔다.

## 사용자 동작

- 설정 상단에 **방송 알림** 탭을 추가했다. 기존 탐색 탭 안의 알림·자동 열기 옵션과 대상 채널 편집기를 한 번만 이동하고, 기존 설정 키·채널 데이터·기존 탭 인덱스를 유지한다.
- 방송 화면 아래와 채널 페이지의 팔로우·구독 영역에 **알림 등록** 버튼을 둔다. 등록 상태는 **알림 등록됨**과 `aria-pressed`로 표현하며 다시 누르면 해당 채널의 알림 선택을 해제한다.
- 화면 버튼은 해당 채널의 알림 선택만 변경한다. 기존 자동 열기 선택을 보존하며 새 대상의 자동 열기는 꺼짐이다. 전체 알림이 꺼져 있으면 등록 후 전용 탭에서 전체 알림을 켜도록 안내한다. 전체 옵션 저장과 알림 권한 요청은 기존 설정 화면의 사용자 조작 안에서 진행한다.
- 설정 화면, 다른 탭의 화면 버튼과 로컬 채널 목록을 동기화한다. 등록 채널은 최대 32개다. 등록 해제는 채널별 알림 선택을 끄며 목록에서의 삭제는 설정 화면에서 수행한다.

## 저장·수명주기

- 백그라운드의 기존 직렬 큐가 채널 변경을 소유한다. 콘텐츠 스크립트가 저장소에 직접 쓰지 않는다.
- 화면 등록 메시지는 같은 확장의 치지직 최상위 탭에서 온 요청만 받는다. 발신 컨텍스트의 URL 경로를 현재 채널 ID와 비교하지 않으며, 버튼 실행 직전에 확인한 채널 ID를 사용한다. 화면에는 알림 등록 명령만 허용하며, 전체 목록 삭제·자동 열기 변경은 허용하지 않는다.
- 새 대상은 기존 채널 API로 ID와 이름을 확인한다. 페이지가 보낸 채널명은 신뢰하지 않는다. 기존 대상의 재등록·해제에는 추가 조회가 없고 동시에 같은 대상을 등록해도 첫 저장 이후 중복 조회하지 않는다.
- 버튼 실행 직전에 라우트와 현재 DOM 소유권을 다시 확인한다. SPA 이동·네이티브 영역 교체·노드 재삽입·pagehide/pageshow에 맞춰 관찰자와 버튼을 정리·복원한다. 늦게 온 저장 응답이 다음 채널 화면이나 더 최신 저장소 변경을 덮지 못하게 한다.
- 관찰 대상은 `#layout-body`이고, 실제 컨트롤·채널 링크의 변경만 단일 RAF로 합친다. 관련 없는 채팅·목록 mutation으로 전체 화면을 다시 조회하거나 네트워크를 요청하지 않는다.
- 이미 켜진 전체 알림에 새 채널을 등록해도 현재 진행 중인 방송은 기존 기준값으로만 저장하고, 이후 새 방송부터 알린다.

## 발신 주소 제한 수정

- 사용자가 정상 등록 버튼을 눌러도 `현재 채널이나 설정 화면에서 다시 시도해 주세요.`가 표시된다고 보고했다. 해당 문구는 저장 전 발신자 검사에서만 반환된다. 사용자의 실제 MessageSender 값은 수집하지 못했다.
- 기존 검사는 `sender.url`에서 추출한 채널 ID와 요청 ID의 일치를 요구했다. 홈이나 다른 채널 URL이 남은 발신 컨텍스트로 현재 채널을 등록하는 테스트에서 같은 거부를 재현했다.
- [Chrome MessageSender 문서](https://developer.chrome.com/docs/extensions/reference/api/runtime#type-MessageSender)는 발신 URL을 연결을 연 컨텍스트의 주소로 설명한다. [Chromium ScriptContext 구현](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/extensions/renderer/script_context.h)은 컨텍스트 생성 때 URL을 보관하며, `pushState`와 출처 검사의 차이를 명시한다. [메시지 발신 구현](https://github.com/chromium/chromium/blob/main/extensions/renderer/ipc_message_sender.cc)은 `source_url`에 `script_context->url()`을 넣고, [수신 구현](https://github.com/chromium/chromium/blob/main/extensions/renderer/api/messaging/native_renderer_messaging_service.cc)은 이를 `sender.url`로 전달한다. 사용자가 겪은 세부 조건은 미확인이지만, 발신 컨텍스트 주소를 현재 채널의 정체성으로 사용하는 조건은 제거했다.
- 동일 확장 ID·치지직 HTTPS 출처·최상위 탭·허용된 명령의 검사는 유지한다. 채널 ID 형식과 새 채널의 API 응답을 계속 검증하고, 실제 저장 실패는 성공으로 표시하지 않는다. 콘텐츠 스크립트의 현재 라우트·DOM 소유권 검사는 기존대로 유지한다.
- 회귀 검사는 홈 진입 후 채널 이동과 다른 채널에서 이동한 상황의 등록·해제를 검증하며, 이전 채널 설정이 바뀌지 않는지도 확인한다. 다른 채널의 발신 URL을 무조건 거부하던 기존 검사는 이 동작 계약에 맞춰 교체하고, 외부·유사 도메인·HTTP·잘못된 채널 ID 거부는 별도로 검증한다.

## 검증

- 전용 탭과 화면 등록 요청의 최초 실패를 확인한 뒤 구현했다.
- 관련 옵션·알림·화면 등록 검사 49개 통과. 등록·해제, 권한 승인/거부의 기존 계약, 자동 열기·전체 옵션 보존, 채널 한도·조회/저장 오류, 발신자 검증, 중복 조회, 기존 방송 건너뛰기, 키보드 탭 이동, SPA·재마운트·늦은 응답·불필요한 재조회 방지를 검사했다.
- 전체 `npm.cmd run test:all` 879개, `npm.cmd run lint`, `npm.cmd run format:check`, `git diff --check` 통과. 전체 검사는 당시 같은 작업 트리에 존재한 다른 후원 기록 변경도 포함한다. 이 작업에서 해당 변경을 수정하거나 되돌리지는 않았다.
- 코드에서 hover·focus·active·저장 중·오류 상태, 현재 색상 토큰, 접근 가능한 이름과 상태 메시지, reduced-motion 처리를 확인했다. 움직임은 150ms의 누름 피드백에만 적용하며 컬러 전환은 테마를 즉시 따른다. 정적 기본 색상에서 등록 상태 텍스트의 대비는 약 4.89:1이다.
- 실제 브라우저의 라이트·다크 화면, 좁은 옵션 팝업과 네이티브 버튼 사이의 배치, 재로드 후 주입은 아직 직접 검증하지 못했다. 컴퓨터 사용 도구는 사용자 지침에 따라 사용하지 않았다.

수동 확인은 확장을 다시 로드하고 치지직 탭을 새로고침한 뒤 진행한다. 설정의 방송 알림 탭, 라이브 하단·채널 페이지의 버튼, 등록 상태의 양방향 동기화, 다른 채널로 이동한 뒤 대상 전환을 확인한다. 전체 알림을 끈 상태에서도 대상 등록은 가능하되 설정 안내가 표시되고, 기존 자동 열기 선택이 유지되는지 확인한다.

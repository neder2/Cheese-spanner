## 1 합성 클릭으로 고정 채널 목록을 변경할 수 있어요

**우선순위와 상태:** P2 · 자동 재현 완료 · 미수정

### 재현 조건과 절차

팔로잉 고정 기능이 켜져 있고, 사이드바에 고정 모드 버튼과 정상 채널 행이 표시된 상태예요. 테스트 저장소의 초기 고정 목록은 비워 둬요.

1. 사용자 입력 없이 페이지 스크립트에 해당하는 방식으로 고정 모드 버튼의 `.click()`을 호출해요.
2. 고정 모드가 켜진 뒤 정상 채널 행의 링크에 `.click()`을 호출해요.
3. 두 이벤트의 `isTrusted`와 설정 저장 결과를 확인해요.

### 기대 동작과 실제 결과

**기대:** 실제 사용자 입력이 아닌 합성 클릭으로는 고정 목록 저장이 시작되지 않아야 해요.

**실제:** 두 이벤트의 `isTrusted`가 모두 `false`인데도 테스트 채널 `channel-c`가 sync 고정 목록에 저장됐어요.

```text

고정 목록: [] → ["channel-c"]
```

### 원인과 영향

[sidebarCustomization.js의 클릭 처리](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/features/sidebarCustomization.js:1228)는 합성 입력 여부를 검사하지 않고 고정 모드를 전환해요. 같은 처리의 [저장 분기](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/features/sidebarCustomization.js:1245)도 `togglePinned()`를 호출하기 전에 신뢰한 입력인지 확인하지 않아요. [Space 키 처리](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/features/sidebarCustomization.js:1257)에도 같은 검사가 없지만, 이번 실행 재현은 클릭 경로로 했어요.

치지직 문서에서 실행되는 페이지 스크립트가 실제 사용자 조작 없이 고정 채널 목록을 바꿀 수 있는 경로예요. 확인한 영향은 고정 목록의 sync 저장이며, 쿠키 접근이나 다른 모든 설정의 변경까지 입증한 것은 아니에요. [설정 저장 보안 기준](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/docs/security.md:78)의 합성 이벤트 저장 금지와 맞지 않아요.

### 수정 방향과 완료 기준

고정 모드 진입과 저장을 시작하는 클릭·키 처리에서 신뢰한 사용자 입력을 확인해야 해요. 저장 직전에는 대상이 현재 팔로잉 목록의 정상 채널 행인지도 확인해야 해요.

## 2 부분 설정 파일이 가져오지 않은 단축키의 동작까지 바꿔요

**우선순위와 상태:** P2 · 계획 및 저장 컨트롤러 재현 완료 · 미수정

### 재현 조건과 절차

세 배속 단축키가 모두 저장되어 있고 서로 중복되지 않는 정상 구성을 사용해요.

| 기능        | 기존 저장값   | 부분 파일의 값 |
| ----------- | ------------- | -------------- |
| 절반 배속   | `KeyQ`        | `BracketLeft`  |
| 두 배 배속  | `BracketLeft` | 포함하지 않음  |
| 배속 초기화 | `KeyW`        | 포함하지 않음  |

1. 부분 설정 파일의 `sync.options`에 `playbackSpeedHalfKeyCode: "BracketLeft"`만 넣어요.
2. 설정 저장 컨트롤러의 미리보기 요청을 실행해요.
3. 반환받은 fingerprint로 같은 파일의 적용 요청을 실행해요.
4. 원시 저장값과 `normalizeOptions()`를 거친 실제 사용값을 비교해요.

### 기대 동작과 실제 결과

**기대:** 가져올 키가 기존 두 배 배속 키와 충돌하므로 적용 전에 거절해야 해요. 파일에 없는 단축키는 유지해야 해요.

**실제:** 미리보기는 옵션 1개 변경으로 안내하고 적용 결과는 `applied`였어요. 원시 저장값에 중복이 생기면서 소비자는 세 단축키를 기본 조합으로 사용했어요.

| 기능        | 적용 후 원시 저장값 | 적용 후 실제 사용값 |
| ----------- | ------------------- | ------------------- |
| 절반 배속   | `BracketLeft`       | `BracketLeft`       |
| 두 배 배속  | `BracketLeft`       | `BracketRight`      |
| 배속 초기화 | `KeyW`              | `Backslash`         |

### 원인과 영향

[settingsBackup.js의 조합 검사](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/shared/settingsBackup.js:497)는 정규화 결과를 파일에 포함된 키에 대해서만 비교해요. 중복으로 세 키가 기본값으로 정규화되더라도 가져온 절반 배속 값이 이미 기본값인 `BracketLeft`라서 검사를 통과해요. 저장 단계는 절반 배속 키만 쓰며, 이후 [설정 정규화](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/shared/settings.js:357)가 중복된 세 키를 기본 조합으로 사용하게 해요.

파일에 없는 두 배·초기화 키의 원시 저장값은 보존되지만, 실제 단축키 동작은 달라져요. 따라서 사용자에게 표시한 변경 범위와 적용 효과가 일치하지 않아요. 일부 저장키가 없어서 생기는 기본값 채움 문제와 달리, 이 재현은 세 키가 모두 정상 저장된 상태에서 발생해요.

### 수정 방향과 완료 기준

가져온 키와 유지할 키를 병합한 뒤 배속 단축키 세 개를 한 조합으로 검사해야 해요. 충돌하는 부분 파일은 저장 전에 `option-combination` 등 기존 오류 경로로 거절하는 방향이 적절해요.

- 충돌하는 부분 파일의 미리보기·적용이 저장을 만들지 않아요.
- 거절 뒤 원시 저장값과 실제 사용값이 모두 유지돼요.
- 충돌하지 않는 부분 파일과 유효한 전체 파일은 정상 적용돼요.
- 미리보기 이후 다른 탭에서 단축키가 바뀌는 경우도 재확인해요.

## 3 카드 주소가 바뀌어도 이전 채널의 방제가 남아요

**우선순위와 상태:** P2 · 자동 재현 완료 · 미수정

### 재현 조건과 절차

팔로잉 화면의 채널 A에 저장된 이전 방제가 있고, 현재 방송 ID 확인이 성공해 방제 버튼이 표시된 상태예요.

1. 채널 A의 이전 방제 패널을 열고 초기 화면 동기화가 끝날 때까지 기다려요.
2. 같은 제목 링크 노드를 유지하면서 `href`만 채널 B의 라이브 주소로 바꿔요. 제목 텍스트는 그대로 둬요.
3. 별도 텍스트 변경이나 화면 크기 변경 없이 버튼과 열린 패널을 확인해요.

### 기대 동작과 실제 결과

**기대:** 링크가 다른 채널을 가리키면 A의 방제 버튼과 열린 패널을 정리해야 해요. B의 이력은 B의 현재 방송을 확인한 뒤에만 표시해야 해요.

**실제:** 링크는 B를 가리키지만 버튼과 열린 패널은 A의 이력을 유지했어요.

```text
현재 링크: /live/channel-456
버튼의 채널 ID: channel-123
패널 열림: true
패널 내용: 이전 제목
```

### 원인과 영향

[followingTitleHistory.js의 DOM 감시](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/features/followingTitleHistory.js:508)는 자식 노드·텍스트 변경만 관찰해서 `href` 변경만으로는 다시 확인하지 않아요. [버튼의 클릭 처리](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/features/followingTitleHistory.js:281)도 생성 당시의 채널 ID를 사용하며, 사용 직전에 현재 링크의 채널을 다시 확인하지 않아요.

다른 채널의 방제를 현재 카드의 이력으로 오인할 수 있어요. 저장 기록이 다른 채널에 합쳐지는 문제는 아니에요. 실제 치지직이 같은 제목을 유지한 채 주소만 교체하는 순서는 이번에 측정하지 않았으며, 해당 조건을 만든 자동 DOM 검사에서 확인한 결과예요.

### 수정 방향과 완료 기준

관련 제목 링크의 `href` 변경을 감지하고, 버튼 사용 직전에도 현재 링크와 보관한 채널 ID가 일치하는지 확인해야 해요.

- 주소만 바뀌어도 기존 버튼과 열린 패널이 남지 않아요.
- 주소·제목이 순차적으로 갱신되는 동안 서로 다른 채널의 자료를 섞어 표시하지 않아요.
- 새 채널에 유효한 이력이 있으면 방송 확인 후 올바른 버튼을 표시해요.
- 기존 방제 패널의 반복 다시 그리기 방지와 텍스트 선택 동작을 유지해요.

## 4 방송 확인이 만료돼도 조회 실패 후 이전 방송 방제가 보여요

**우선순위와 상태:** P2 · 자동 재현 완료 · 미수정

### 재현 조건과 절차

채널의 방송 `live-1`에 이전 방제가 저장되어 있고 현재 방송 확인도 성공한 상태예요. 같은 채널이 같은 제목으로 `live-2`를 시작했지만, 수집 저장소에는 아직 `live-1` 이력이 남아 있는 조건을 모사해요.

1. 첫 방송 확인을 완료하고 이전 방제 버튼을 표시해요.
2. 테스트 시각을 121초 전진시켜 2분의 확인 유효기간을 넘겨요.
3. 카드의 시청자 수 영역을 변경해 화면 동기화를 발생시켜요.
4. 재확인용 live-detail 요청을 네트워크 오류로 실패시켜요.
5. 남아 있는 방제 버튼을 눌러 패널 내용을 확인해요.

### 기대 동작과 실제 결과

**기대:** 방송 확인이 만료되었고 현재 방송도 확인하지 못했다면, 이전 방송 이력을 현재 방송의 이력으로 제공하지 않아야 해요.

**실제:** 재확인 요청은 실행됐지만, 실패 후에도 버튼과 이전 `live-1`의 방제 패널을 계속 열 수 있었어요.

```text
모사한 현재 방송: live-2
방송 확인 요청 수: 2
이전 방제 버튼 존재: true
패널 열림: true
패널 내용: 이전 제목
```

### 원인과 영향

[shouldVerify()](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/features/followingTitleHistory.js:316)는 2분 만료를 새 조회 조건으로 사용해요. 그러나 표시 자료를 반환하는 [getVerifiedEntry()](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/features/followingTitleHistory.js:308)는 확인 시각을 검사하지 않아요. 조회 실패도 기존 확인값을 무효화하지 않아, 만료된 확인값으로 표시가 계속 허용돼요.

같은 제목으로 다시 켠 방송에서 이전 방송의 방제가 현재 방송 이력처럼 보일 수 있어요. 기존 문서의 ‘최대 2분 남짓’은 재확인 성공을 전제로 하며, 재확인이 실패하면 그 시간 안에 사라진다는 보장이 없어요. 이 재현은 네트워크 오류와 시각 전진을 모사했으며 저장 이력의 손상은 확인되지 않았어요.

### 수정 방향과 완료 기준

이력을 표시하거나 패널을 열 때 확인 유효기간을 검사해야 해요. 만료된 상태의 요청 중·실패 구간에는 예전 확인값을 현재 방송의 증거로 사용하지 않고, 새 확인 성공 후 표시 여부를 결정해야 해요.

- 유효기간이 지난 뒤 재조회 중이거나 실패한 경우 이전 방송의 버튼·패널이 노출되지 않아요.
- 같은 방송으로 재확인되면 기존 이력을 다시 사용할 수 있어요.
- 새 방송으로 확인되면 이전 방송 이력을 표시하지 않아요.
- 재시도 간격과 동시 요청 제한을 유지해요.

2. 크기 손잡이를 패널이 작아지는 방향으로 최소 크기까지 끌어요.
3. 드래그 중 크기를 기록해요.
4. 손잡이를 놓고 설정 저장 완료 후 크기를 다시 확인해요.

### 기대 동작과 실제 결과

**기대:** 드래그 중 허용된 크기로 놓았다면 저장 완료 후에도 그 크기를 유지해야 해요. 저장할 수 없는 크기라면 드래그 단계부터 제한해야 해요.

**실제:** 모의 레이아웃에서 아래와 같이 패널이 커졌어요. 이 수치는 실제 Chrome 측정값은 아니에요.

| 시점              | 패널 너비 | 패널 높이 |
| ----------------- | --------- | --------- |
| 드래그 중         | 176px     | 134px     |
| 놓은 뒤 저장 완료 | 248px     | 188px     |

저장된 한 칸 크기는 `chatWidth: 240`, `chatHeight: 180`이었고 채팅 크기 70% 설정은 유지됐어요.

### 원인과 영향

[chatMultiview.js의 드래그 크기 계산](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/features/chatMultiview.js:1301)은 70% 배율을 반영한 한 칸 최소 크기 168×126px를 허용해요. 그러나 저장에 사용하는 [withChatSize()](/Users/home/Documents/Codex/2026-10-01/task-2/Chzzk/shared/chatMultiview.js:271)는 배율과 무관하게 최소 240×180px로 제한해요. 여백을 포함한 표시 크기가 저장 완료 후 다시 계산되면서 패널이 커져요.

사용자가 놓은 경계와 최종 패널 크기가 달라져 작은 채팅창 배치를 유지하기 어려워요. 드래그 범위와 저장 범위가 다르다는 것이 원인이며, 이번 실행 재현은 70% 최소 크기 조건으로 한정해요.

### 수정 방향과 완료 기준

표시 단계와 저장 모델에서 같은 크기 단위와 제한을 사용해야 해요. 저장 크기를 실제 표시 픽셀로 유지할지, 배율 적용 전 크기로 해석할지는 모델 계약과 함께 정해야 해요.

- 70%, 100%, 150%에서 손잡이를 놓은 뒤 크기가 튀지 않아요.
- 입력창 ON·OFF와 여러 칸 배치에서도 표시·저장 제한이 일치해요.
- 큰 화면의 저장 상한과 좁은 화면의 표시 제한을 함께 확인해요.
- 드래그 취소는 저장하지 않고 원래 크기로 돌아가요.

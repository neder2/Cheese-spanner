# 치즈 스패너 작업·검증 규칙

## 작업 범위와 Git

- 시작할 때 현재 branch, HEAD, `git status`, 기존 diff와 요청한 branch·version을 확인해요. 요청 대상과 현재 branch가 다르면 구현 전에 멈추고 차이를 보고해요.
- 다른 버전·기능의 계획, fixture, 테스트, 문서를 같은 작업에 섞지 않아요. 기존 변경과 미추적 파일을 되돌리거나 덮어쓰거나 삭제하지 않아요. 충돌 가능성이 있으면 먼저 보고해요.
- 새 branch 생성·전환은 요청받았거나 필요성을 합의한 경우에만 해요. 버전 branch는 `1.4.1`처럼 버전 번호만 쓰고 접두어를 붙이지 않아요.
- 커밋·push·병합·태그·버전 증가·GitHub Release 생성은 각각 명시적인 요청이 있을 때만 해요. `reset --hard`, `clean`, 강제 push 등은 명시적 요청과 정확한 대상 확인 없이 실행하지 않아요.
- 리뷰 요청이면 읽기 전용 근거와 결과를 먼저 보고하고, 계획 요청이면 구현 전 계획에서 멈춰요. 구현 요청이면 안전한 범위의 구현과 검증까지 마쳐요.
- 무관한 정리·이름 변경·전면 포맷은 기능 변경에 섞지 않아요. 상수·호출부 확인은 직접 검색하고, 큰 파일은 정의·호출·테스트·인접 상태를 필요한 범위부터 읽어요.
- 하위 에이전트는 독립적으로 나눌 수 있는 큰 조사에만 최소한으로 사용하고 작업 경계도 전달해요. 사용자에게 표시하는 에이전트 이름 오른쪽에 모델명을 명시해요.
- 사용자에게 한국어 존댓말·해요체로 답해요. 수행한 검증과 수행하지 못한 검증을 구분하고, 코드로 알 수 없는 제품 의도를 확정하지 않아요.

## 런타임·의존성 경계

- 권한은 필요한 최소 범위로 유지해요. 새 권한·match pattern을 추가하기 전에 필요성·대안·사용 시점과 설치·업데이트 경고 영향을 검토해요. 상시 필요하지 않은 host 접근은 가능한 경우 `optional_host_permissions`로 두고 사용자 동작 안에서 요청해요.
- 별도 아키텍처 변경 요청 없이 번들러, 런타임 ESM, `import`/`export`, 생성된 런타임 배포 코드를 도입하지 않아요. 기존 IIFE와 전역 네임스페이스 연결을 유지해요.
- 공용 모듈은 manifest에서 소비자보다 먼저 로드해요. 서비스 워커의 `importScripts()`와 각 HTML script 목록도 별도로 확인해요. 정적 manifest 밖의 동적 등록은 등록 코드와 함께 검증해요.
- MAIN과 isolated의 전역을 직접 공유한다고 가정하지 않아요. MAIN은 기존 DOM 속성·이벤트 브리지로만 기능 설정·결과를 교환하고 확장 저장소·메시지·특권 API·직접 네트워크 호출을 추가하지 않아요.
- 워커가 사용하는 공용 파일에서는 DOM 전역을 무가드로 참조하지 않아요. `shared/`의 모든 파일이 워커 호환이라고 가정하지 않아요.
- `BetterChzzk.utils`를 교체하지 말고 병합해요. 공용 구현이 있는지 확인한 뒤 새 유틸을 만들고, 새 추상화는 실제 중복과 둘 이상의 소비자가 확인될 때 도입해요.
- `shared/settings.js`의 `OPTION_SCHEMA`가 옵션 정의의 단일 공급원이에요. 공개 키·시그니처를 임의로 바꾸지 않아요. 옵션 수정 시 HTML의 `data-option`·`data-depends-on`, 저장·권한 흐름, feature의 적용·정리, 테스트와 사용자 설명을 함께 확인해요.
- 시청 기록 저장은 background 단일 writer를 통과해요. 콘텐츠 기능과 기록 페이지에서 직접 read-modify-write를 추가하지 않아요. 다른 local 키의 개별 소유권까지 시청 기록 큐로 임의 통합하지 않아요.
- 콜백형 storage API는 같은 콜백 안에서 `chrome.runtime.lastError`를 즉시 확인해요. 가능한 경우 기존 Promise 래퍼나 `getStorageLastError`를 재사용해요.
- isolated 기능의 SPA 이동은 `startPageChangeDetection(handler)`를 사용해요. 각 feature에서 history API를 다시 패치하지 않아요.

## 수정 원칙

증상을 재현해 기대 동작과 실제 동작을 나누고, 이벤트·상태·DOM·응답 흐름에서 최초로 잘못된 값이나 분기가 생긴 곳을 찾아요. 원인을 소유한 파일·함수에서 최소한으로 수정하고 가능하면 수정 전 실패·수정 후 통과하는 회귀 테스트를 추가해요.

타이머·재시도·광범위 DOM 스캔을 먼저 늘리거나 기존 기능을 끄는 방식으로 증상을 숨기지 않아요. 페이지 기능의 실패를 새 탭·창·팝업·iframe·다른 페이지로 우회하지 않아요. 원격 코드 실행, 가짜 데이터·문구·진행률·썸네일, 실패를 성공처럼 표시하는 경로는 추가하지 않아요.

`null` 가드, 파싱 기본값, 캐시 미스 처리, 기능 감지, CSS 기본값과 실측된 응답 형식 선택은 허용해요. 새 호환 분기는 실측된 변형, 결정적인 선택 조건, 회귀 테스트가 있어야 해요. 외부 장애를 직접 고칠 수 없으면 실패 조건·영향·근거를 보고해요.

## DOM·비동기 수명주기

- DOM 객체를 영구적인 메시지·댓글·카드 ID로 사용하지 않아요. marker·expando·WeakMap을 재사용하기 전에 원본 ID·현재 속성·작성자·본문·재사용 신호로 현재 정체성을 검증해요.
- 여러 mutation에 걸쳐 갱신되는 닉네임·배지·본문을 혼합 상태로 확정하지 않아요. 단순 지연 증가 대신 세대·정체성·안정화 조건을 확인해요.
- 보관한 원본 노드로 이동·클릭·스타일 복사를 하기 직전에 정체성을 다시 검증해요. React 소유 트리를 불필요하게 비우거나 재부모화하지 않고 확장 소유 요소만 필요한 만큼 재부착해요.
- observer, listener, timer, RAF, abort controller는 옵션 비활성화·라우트 변경·DOM 교체에 맞게 정리해요. 재마운트 후 중복 등록과 늦은 콜백의 재시작을 막아요.
- 라우트·대상 종속 요청에는 가능한 경우 AbortSignal을 전달하고 generation·token·현재 대상 확인으로 늦은 응답을 차단해요. `AbortError` 이름만 보고 사용자 취소와 내부 타임아웃을 같은 의미로 처리하지 않아요.
- 보조 조회 실패가 핵심 데이터 폐기로 이어져야 하는지 계약을 확인해요. 확인된 핵심 자료로 안전하게 계산할 수 있으면 보조 조회만 중단하고, 미측정 값을 성공처럼 만들지 않아요.
- 캐시에는 상한·무효화 조건을 두고 취소·실패 Promise와 소비자별 signal의 영향을 명확히 해요. 공유 요청과 foreground·prefetch 중복을 확인해요. 경로와 무관한 bounded 캐시를 보존하는 기존 계약까지 무조건 없애지 않아요.
- 전체 목록 재스캔·무제한 캐시·짧은 반복 타이머·중복 네트워크 요청을 추가하지 않아요. DOM 변화는 가능한 한 변경 후보와 제한된 범위에서 처리해요.

## UI·호환성

치지직에 삽입하는 UI는 현재 네이티브 디자인과 실제 시맨틱 토큰을 먼저 확인해요. 정적 기본값도 제공하며, 토큰이 없고 정확한 일치가 필요하면 computed style 복사를 검토해요. 복사값은 테마·DOM 교체 때 다시 동기화해요. 넓은 `[class*="dark"]` 판별을 근거 없이 추가하지 않아요.

변경 UI는 라이트·다크, 좁은 옵션 팝업, 긴 한글, 키보드와 focus를 확인해요. 클릭 요소는 적절한 타입·이름·키보드 동작을 제공하고 button은 `type="button"`을 사용해요. 작은 글씨의 기호 나열 대신 의미가 드러나는 문구를 써요. 로딩·빈 결과·오류는 실제 상태만 표시해요.

치지직 DOM·React·API·HLS 구성은 외부 의존이에요. 관련 문제 수정 전 현재 화면·응답을 다시 측정해요. 과거 지연값·playlist 태그·mux 구성·토큰 개수를 영구 보장으로 고정하지 않아요. 실측 기록에는 날짜·대상 URL 또는 endpoint·필드나 태그·재현 조건을 남기며 fixture를 모든 현재 방송의 증거로 취급하지 않아요.

`BetterChzzk`, `betterchzzk-*`, 기존 저장 키는 호환 식별자예요. 제품명만 바뀌었다고 일괄 치환하지 않아요. 새 DOM 마커는 기존 ID와 기능별 `data-bc*` 관례를 따라요. 구조 변경 시 관련 주석도 갱신하되 모든 파일에 큰 헤더를 일괄 추가하지 않아요.

## 폐기·실험 기능의 검증 경계

공개 실험 기능과 개발 전용 파일을 구분해요. 파일·테스트가 존재한다는 이유로 manifest·옵션·배포에 넣지 않아요. 현재 `adAutoSkipEnabled`의 오래된 저장값은 활성화로 이어지지 않아야 해요. 개발용 광고 SKIP 테스트를 기본 배포 안전 검사와 혼동하지 않아요.

폐기한 그리드 재생정보 변조, 자동 단축키 실패 감지, 이전 업데이트 공지를 새 기능의 기본값으로 되살리지 않아요. `screenShortcutsEnabled`는 옛 `shortcutRescueEnabled`와 독립적이며 기본 꺼짐이에요. 보관된 공지 템플릿을 재사용하려면 별도 요구와 새 표시 조건을 검토해요.

## 검증 기준

검증 범위는 변경의 영향에 맞춰 정해요. 작은 구현마다 전체 검사를 반복하지 않으며, 기능 내부 변경은 해당 기능과 직접 영향받는 인접 기능의 테스트, 변경한 JS 파일의 lint, 변경 파일의 포맷 검사로 마쳐요. 테스트는 파일명만 보고 고르지 않고 호출부·공유 상태·소비자를 확인해 선택해요.

- 문서·주석·표현만 바꾸고 실행 동작·계약에 영향이 없으면 변경 파일의 포맷·내용·링크를 확인해요. 런타임 테스트와 전체 lint는 생략할 수 있어요. 주석도 검사하는 정적 안전 정책에 걸리는 변경이면 해당 검사를 추가해요.
- 공용 유틸이나 테스트 helper를 바꾸면 직접 테스트와 영향을 받는 소비자의 테스트까지 넓혀요. 소비자를 확인할 수 있으면 관련 범위로 검증하고, 영향 범위를 특정하기 어렵거나 여러 기능을 넓게 바꿨다면 전체 검증을 해요.
- 설정 스키마·저장 형식·쓰기 큐·권한·발신자 검증·world·스크립트 로딩 순서·manifest, 의존성이나 테스트 실행·검사 설정을 바꾸면 관련 검사 후 전체 검증을 해요. 릴리스 전과 사용자가 전체 검사를 요청한 경우에도 전체 검증을 해요.
- 전체 검증은 `npm.cmd run test:all -- --test-concurrency=2`, `npm.cmd run lint`, `npm.cmd run format:check`를 순서대로 실행해요. 한 작업의 변경이 모인 시점에 한 번 수행하고, 통과 후에는 새 변경·실패·미해결 우려가 영향을 주는 검사만 다시 실행해요. 실행 코드가 바뀌지 않은 후속 문서 편집은 문서 검사만 다시 해요.

관련 테스트도 `node --test --test-concurrency=2 <관련 테스트 파일들>`로 동시 실행을 최대 2개로 제한해요. 같은 PC에서 여러 테스트 묶음을 겹쳐 실행하지 않고, 테스트·lint·포맷 검사는 차례로 실행해요. 여러 에이전트가 작업해도 검증 실행은 조율해 동시에 부하를 만들지 않아요.

결과에는 실행한 검사와 영향 범위, 전체 검사를 생략했다면 그 이유를 짧게 남겨요. 통과를 위해 테스트를 삭제하거나 assertion을 약하게 만들지 않아요. 제품 계약 변경으로 기존 테스트를 수정한다면 바뀐 계약과 대체 회귀 범위를 설명해요.

테스트는 사용자 동작·상태 전이·호출 횟수·부작용을 우선해요. 성능은 중복 예약·요청·파싱·재스캔 여부로 검사하며 함수명·소스 길이에 불필요하게 고정하지 않아요. 원격 실행·권한·패키징·world·단일 writer 같은 정적 정책 검사는 유지해요. 옵션 UI는 장식 수치·그룹 수·순서보다 의존성·접근성·팝업 사용성을 보호해요.

JSDOM fixture는 실패해도 닫고 observer·비동기 작업을 먼저 정리해요. 성공 대기는 조건 대기를 우선하고, ‘동작하지 않아야 하는 구간’의 대기에는 근거를 남겨요. 정적 안전 검사는 주석도 검사하므로 금지 패턴을 주석에 넣는 변경도 확인해요.

전체 포맷 검사가 범위 밖 기존 차이 때문에 실패하면 원인을 따로 보고하고 변경 파일만 다시 검사해요. 이를 핑계로 범위 밖 파일을 포맷하지 않아요.

화면 검증은 브라우저 도구를 사용해요. 컴퓨터 사용 도구는 사용자가 다시 명시적으로 요청하기 전에는 사용하지 않아요. 확장 관리·확장 페이지 접근이 차단되면 우회하지 않아요. 실제 확장 ID·실행 context·DOM 마커·기능 UI 없이 명령 성공만으로 주입을 확정하지 않아요. 미검증 범위와 최소 수동 절차를 보고해요.

## 릴리스·고지

1.4.1부터 새 기능 안내 검증은 변경 규모와 무관하게 매 릴리스의 필수 조건이에요. 릴리스 준비 완료 보고·릴리스 제안·승인 요청 전에 대상 버전의 안내 내용, 설치 버전 일치, 프로필 전체의 최초 1회 표시, 20초·호버·초점 동작, 끄기·다시보기·설정 이동, 시청을 방해하지 않는 실제 Chrome 화면과 배포 파일 포함 여부를 확인해요. 오류 수정만 있는 버전도 대상 버전의 짧은 요약을 준비하고 같은 점검을 수행해요.

자동 검사 통과만으로 실제 화면 확인을 대체하지 않아요. 대상 버전·검증한 소스·명령과 종료 코드·실제 브라우저 확인 결과를 해당 릴리스 검증 기록에 남겨요. 내용이나 동작이 바뀌면 영향을 받는 검증을 다시 수행해요. 미검증·실패·잘못된 안내가 남으면 준비 완료나 릴리스 승인을 요청하지 않고, 이미 릴리스 요청을 받았더라도 공개·스토어 제출 전에 해결해요. 브라우저 접근이 막히면 미완료 항목과 필요한 수동 확인을 알리며, 도구 사용 제한을 우회하거나 사용자 수동 확인이 끝난 것으로 추정하지 않아요.

현재 제품명은 치즈 스패너, 영문명은 Cheese Spanner, 개발 패키지명은 `cheese-spanner`예요. 새 제목과 현행 제품 문서에 이 이름을 쓰며 과거 이력·출처의 당시 이름은 유지할 수 있어요. 커밋을 요청받으면 첫 줄은 `Cheese Spanner <version>` 형식으로 작성해요.

버전 변경 시 manifest·package를 함께 맞춰요. 릴리스·버전 업데이트에는 업데이트 내역을, 기능·옵션·조작·권한 변경에는 README를 같은 릴리스에서 갱신해요. 데이터 처리 변경에는 PRIVACY, 서드파티 코드·라이선스 변경에는 THIRD_PARTY_NOTICES와 소스 고지를 확인해요. 스토어 문구 변경이 필요하면 외부 작업이라는 이유로 누락하지 말고 변경 내용을 보고해요.

릴리스 설명은 직전 배포 버전과 최종 사용자 동작의 차이로 작성해요. 같은 버전 개발 중 생겼다가 해결한 문제를 배포 버그 수정으로 올리지 않아요. 새 기능은 완성된 조작법으로 설명하고 개발 단계별 작업, 테스트 개수, lint·포맷·ZIP·브라우저 검증 보고는 별도 작업 기록에 남겨요. GitHub Release 본문은 업데이트 내역과 맞춰요.

`volumeTooltip.js`, `chatTimestampPage.js`의 cheese-knife/jebibot 출처와 THIRD_PARTY_NOTICES를 함께 유지해요. vendor 파일을 바꾸면 원본 버전·라이선스·패키지 동봉 상태도 확인해요.
